## サマリー

`rules/hve/clean-architecture.md` のクライアント（フロントエンド・モバイル）の節を、原則だけの記述から具体的な規約にするための未決事項を決める。手元の調査（2026-10-31）: クライアントは paddock/web（React 19 + Vite + TS の SPA。`api/`・`lib/`・`routes/` の 3 区分。サーバ状態は TanStack Query）と 非公開のモバイルクライアント（Flutter。レイヤー分けなし）の 2 つで、どちらもレイヤー分けをしていない。手本のテンプレートは無い。上流 HVE にもクライアントの構成の規約は無い。現行規約は「既存コードがこの規約の構成でなければ既存コードに合わせる」ので、新しい規約が効くのは主に新しいクライアント。

Q07・Q08 は、Q02 の回答（Web とモバイルで分ける）で生じた追加の質問で、会話（AskUserQuestion）で確認した。Flutter の公式ガイド（https://docs.flutter.dev/app-architecture/guide 、2026-10-31 に参照）は、UI 層（View・ViewModel）と Data 層（Repository・Service）を基本とし、Domain 層（Use-case）を任意としている。ガイド自体はディレクトリ構成を定めていないが、case study（https://docs.flutter.dev/app-architecture/case-study ）の Package structure の節がパッケージ構成を推奨している（計画の敵対的レビューの指摘で確認。規約は case study を基にした）。

[Q01]
- 対象ドキュメント: rules/hve/clean-architecture.md
- 該当箇所: ## クライアント（フロントエンド・モバイル）
- 問題種別: 不明瞭
- 重大度: critical
- 質問内容: クライアントの具体的な規約を、どの範囲で作りますか？
- 選択肢: A) 作る。フレームワークに依存しない構成を 1 つ定め、手元に実在する React（Web）と Flutter（モバイル）の置き場所を対応表で示す B) 作る。対象はモバイル（Flutter）だけ C) 作る。対象は Web（React）だけ D) 今は作らない。原則だけで運用し、規約に従う新しいクライアントを作るときに改めて決める
- 未回答時の既定値候補: 作る。フレームワークに依存しない構成を 1 つ定め、手元に実在する React（Web）と Flutter（モバイル）の置き場所を対応表で示す
- 既定値候補の理由: #34 の Q4 で PO が「クライアントの具体的な規約は別 Issue で作る」と決めている。対応表に載せる技術を手元に実在する 2 つに限れば、根拠の無い技術を書かずに済む（捏造禁止・YAGNI）
- 未回答のまま進めた場合の影響: 規約の対象と書き方が決まらず、着手できない

[Q03]
- 対象ドキュメント: rules/hve/clean-architecture.md
- 該当箇所: ## クライアント（フロントエンド・モバイル）
- 問題種別: 不明瞭
- 重大度: minor
- 質問内容: 画面を担うレイヤーの名前をどうしますか？
- 選択肢: A) presentation B) controller（バックエンドと揃える） C) ui

- 未回答のまま進めた場合の影響: 命名が決まらない

[Q05]
- 対象ドキュメント: rules/hve/clean-architecture.md
- 該当箇所: ## 未定義の領域
- 問題種別: 不明瞭
- 重大度: minor
- 質問内容: 状態管理・ルーティング・サーバの状態のキャッシュ（TanStack Query・Riverpod など）を、規約で決めますか？
- 選択肢: A) 決めない。「未定義の領域」に足し、各リポジトリが hve-local に書く。どのレイヤーに置くかだけを示す B) フレームワークごとに使うライブラリを規約で決める
- 未回答時の既定値候補: 決めない。「未定義の領域」に足し、各リポジトリが hve-local に書く。どのレイヤーに置くかだけを示す
- 既定値候補の理由: バックエンドでも DB の gateway の構成や認証の置き場所は決めず、各リポジトリの hve-local に任せている。ライブラリはフレームワークごとに違い、手元の 2 つでも揃っていない
- 未回答のまま進めた場合の影響: 規約に書く範囲が決まらない

[Q07]
- 対象ドキュメント: rules/hve/clean-architecture.md
- 該当箇所: ## クライアント（フロントエンド・モバイル）のモバイルの節
- 問題種別: 不明瞭
- 重大度: minor
- 質問内容: Q02 で Web とモバイルを分けたので、モバイル（Flutter）の節のレイヤー名をどうしますか？（Web は公式のガイドが無いので、バックエンドに揃えた model / use-case / gateway / presentation / app にする）
- 選択肢: A) 公式ガイドの名前（ui（view・view_model）/ domain（use-case）/ data（repository・service））。原則に合わせ、repository の抽象を domain 側に置き実装を data に置くと補う。Q03 の presentation は Web にだけ使う B) バックエンドと同じ名前
- 未回答時の既定値候補: 公式ガイドの名前
- 既定値候補の理由: 構成を分けた意図（それぞれの慣習に寄せる）と揃い、Flutter の開発者が読み慣れた名前になる
- 未回答のまま進めた場合の影響: モバイルの節の命名が決まらない

[Q08]
- 対象ドキュメント: rules/hve/clean-architecture.md

- 問題種別: 不明瞭
