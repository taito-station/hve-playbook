# クライアントの認証情報の保持と永続化したキャッシュの破棄の責務を、データの層と use-case に置く

## ステータス

Accepted — 2026-11-03

## 背景と課題

ADR 0031 でクライアント（React の SPA・Flutter）のクリーンアーキテクチャ規約（`rules/hve/clean-architecture.md` のクライアントの節）を定めた。そのセルフレビュー（PR #88）で、セキュリティに関わる 2 点が規約に無いと指摘され、範囲外として見送った（[hve-playbook#101](https://github.com/taito-station/hve-playbook/issues/101)）。

- 認証情報（トークン・セッション）を、どのレイヤーのどの部品が保持するか。端末に保存してよいか、保存するときにどこへ置くか（F10）。0031 は「認証情報の保存先は、未定義の領域の『認証・認可の置き場所』として各リポジトリが決める」としていた
- 端末に永続化したキャッシュ（サーバの状態のキャッシュ・ローカルの保存）を、ログアウト・ユーザー切り替えのときに消す責務を、どのレイヤーに置くか（G6）

規約には「秘密情報・認証情報・個人情報は出さない」の原則はあるが、保持と破棄の方針が無いので、導入先ごとに判断がぶれる。規約が無いまま実装例が増えると、後から揃えるのが難しい。

問い: 認証情報の保持と、永続化したキャッシュの破棄の責務を、クライアントのどのレイヤーに置くか。端末への保存の原則をどこまで規約で定めるか。

## 意思決定の要因

- 共通規約の原則（外部依存はユースケース側の抽象越しに使い、実装は外側のレイヤーが持つ。内側は外側の型・ライブラリを知らない）と、クライアントの節の依存の表（画面の層は gateway・repository を抽象も実装も直接使わない。Web の gateway の依存してよい先は model・use-case だけ）に矛盾しない
- 具体のライブラリや保存領域の名前は、0031・質問票 Q05 の方針どおり各リポジトリの `.claude/rules/hve-local/clean-architecture.md` に任せる。規約が決めるのは責務の置き場所と原則まで
- 認証情報を平文で端末に置かない（Issue の要件）
- 根拠の無い構成を書かない。Flutter 公式 case study の compass app（`compass_app/app/lib/data/repositories/auth/auth_repository_remote.dart`。2026-11-03 に参照）は、認証トークンを data の repository が保持し、API クライアントにはコールバック（`authHeaderProvider`）で渡し、`logout()` で repository が自分の保持分（永続化したトークンとメモリのトークン）を消す
- 責務の置き場所は、質問票ではなく実装計画の承認（Issue #101 のコメント、2026-11-03）で PO が確定した

## 検討した選択肢

- 認証情報はデータの層が保持し、API クライアントは use-case 側の抽象を受け取る。破棄は use-case が保持する層の抽象越しに呼ぶ
- 認証情報を use-case または app（組み立て・起動）が値として持つ
- 破棄を画面の層（ログアウトのボタンの処理）に置く
- 「未定義の領域」の箇条書きに足すだけにし、責務は各リポジトリに任せる

## 決定内容

選択した選択肢: **認証情報はデータの層が保持し、API クライアントは use-case 側の抽象を受け取る。破棄は use-case が保持する層の抽象越しに呼ぶ**。規約のクライアントの節に `### 認証情報と永続化したキャッシュ` を足し、「未定義の領域」に hve-local で決める項目を足した。

- 保持の責務: 認証情報（トークン・セッション）は、データの層（Web は gateway の実装、Flutter は data の repository の実装と service）が保持し、use-case 側の抽象（Web は `src/domain/use-case/gateway/`、Flutter は `lib/domain/repositories/`）越しに扱う。画面の層と use-case は認証情報の値を受け取らず、ログイン・ログアウト・認証済みかの操作だけを扱う（画面の層は use-case 越しに、use-case は抽象越しに）。端末の保存領域は外部依存なので、原則「抽象越しに使い、実装は外側」のとおり。既存の表でも gateway・data がブラウザの保存領域・プラットフォームのラッパーを持つ。compass app も同じ置き場所
- API クライアントが認証情報を受け取る経路: API クライアント（Web は gateway の実装、Flutter は data の service）は、use-case 側に置いた認証情報の抽象を受け取って要求に付け、実装は app（組み立て・起動）が差し込む。要求に付ける値を返す抽象は、データの層だけが呼び、use-case は呼ばない（use-case が扱うのはログイン・ログアウト・認証済みかの操作だけ）。API クライアントは値の写しを持たず、要求のたびに抽象から取る（写しが残ると、ログアウト・ユーザー切り替えの破棄が届かない）。Web は gateway の実装同士を直接 import しない（Web の gateway の依存してよい先は model・use-case だけで、gateway → gateway は表に無い。Flutter は data の repository の実装が service を使う形が case study なので、この制約は Web に限る）。compass app の `authHeaderProvider` コールバックとは形が同じだが、compass は repository 自身が API クライアントに設定し、規約は app が差し込む
- 端末への保存の原則: 保存してよい。保存するときはプラットフォームが保護する保存領域（他のアプリ・スクリプトから読めない領域）を使い、平文のファイルやスクリプトから読める領域に置かない。Web はスクリプトから読める保存領域（localStorage・sessionStorage など）に認証情報を置かず、保存するなら httpOnly の Cookie などスクリプトから読めない仕組みに任せるか、メモリだけに留める。Cookie に任せるときは、保持と要求への付与はブラウザが行い、データの層はログイン・ログアウトの要求を持つ（保持・付与・破棄の責務の記述を、この方式にも当てはめて読めるようにする）。compass app が SharedPreferences（平文）に保存している点には倣わない
- 破棄の責務: ログアウト・ユーザー切り替えのユースケース（use-case の層）が、認証情報・サーバの状態のキャッシュ・ローカルの保存の破棄を、それぞれを保持するデータの層に対する use-case 側の抽象のメソッド越しに呼ぶ。消す処理の実装は保持しているデータの層が持つ（保持する層が消す。順序はユースケースが決める）。画面の層で動くキャッシュ（取得を use-case 経由にして画面の層に置いた形）は、use-case が画面の層を知らないので、画面の層がそのユースケースの完了に合わせて消す
- hve-local で決める項目: 認証情報を保存する端末の領域とライブラリ、Web で端末に保存するかと方式。「未定義の領域」に 1 行足した。0031 の決定「認証情報の保存先は、未定義の領域の『認証・認可の置き場所』として各リポジトリが決める」のうち、本決定は保存先の保持する層と原則を規約で固定し、領域・ライブラリは未定義のまま残す。0031 を狭めるが覆さないので supersede しない。0031 が「認証・認可の置き場所」の行に対応付けた領域・ライブラリは、未定義の領域の新しい行（クライアントが認証情報を保存する端末の領域とライブラリ）に分けた。0031 の「認証・認可の置き場所」の行は変えない
- 書く場所: 責務は Web と Flutter に共通で両方の表の名前を使うので、2 つの表の後に節として足した
- アプリ削除時の扱いは Issue の要件に無いので書かない
- 契約は `tests/test_clean_architecture_contract.sh` の「7) 認証情報と永続化したキャッシュ」で固定する

### 結果（Consequences）

- 良い結果: 認証情報を持つ部品と、ログアウト・ユーザー切り替えで消す責務が決まり、導入先ごとの判断のぶれが減る。画面の層と use-case が認証情報の値を扱わないので、コードの上では、認証情報の値を触る部品がデータの層に限られる（実行時の漏えい（XSS など）への対策は別に要る）
- 悪い結果:
  - 規約の分量がさらに増える（約 12.3KB → 約 15.2KB）。0031 と同じく、クライアントの無いバックエンドのリポジトリでもクライアントの節が載る
  - Web で httpOnly の Cookie に任せるときは、サーバ側の発行・失効と CSRF 対策が要る（スクリプトから Cookie を消せないので、ログアウト時の破棄はサーバ側の失効に依る）。規約は方式の選択を hve-local に任せるだけで、サーバ側の対応は書かない
  - 画面の層で動くキャッシュの破棄を画面の層に置くので、ログアウトの処理が use-case と画面の層の 2 か所に分かれる
  - 導入先は setup.sh を再適用しないと規約が更新されない

## 選択肢の評価（Pros and Cons）

### データの層が保持し、API クライアントは抽象を受け取る。破棄は use-case が抽象越しに呼ぶ（採用）

#### メリット

- 共通規約の原則と依存の表の範囲に収まる。公式 case study の置き場所と同じ

#### デメリット

- 認証情報の抽象と API クライアントの組み立てが app に増える

### use-case または app が認証情報の値を持つ

#### メリット

- トークンを要求に付ける経路が短い

#### デメリット

- 内側（use-case）が外部依存の状態を抱える。app が持つと、組み立て以外の責務が app に増える

### 破棄を画面の層に置く

#### メリット

- ログアウトのボタンの処理に閉じる

#### デメリット

- 画面の層は gateway・repository を直接使えないので、保持している層に届かない

### 「未定義の領域」に足すだけ

#### メリット

- 規約が短く済む

#### デメリット

- 責務の置き場所が決まらず、導入先ごとのぶれを無くすという Issue の目的を満たさない
