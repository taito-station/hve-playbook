# Opus 5.5 向けにプロンプト文面を監査し、規則の食い違いを揃える

## ステータス

Accepted — 2026-09-26

## 背景と課題

skills / rules / agents / CLAUDE.md には、旧モデル向けに書かれた表現が蓄積していた。

- 理由のない「絶対」「必ず」の強調
- 事故経緯の記述
- 判断タスクへの手順の固定
- 件数上限
- ステップごとの定型報告

現行モデル（Claude Opus 5.5）は指示を字義どおりに強く適用するため、これらは過剰適用や硬直の原因になる。

また、同じ規則が複数ファイルに重複し、互いに食い違っていた。

- ADR 配置先（`knowledge/D19/` と `knowledge/adr/`）
- `docs/temp/` の扱い
- review-pr の巡数表記
- ブランチ名・コミット形式

さらに、存在しないツール・skill への参照が残っていた。

## 意思決定の要因

- 文面は短さではなく「現行モデルで有害な特定の表現」を基準に整理する（理由・契約・脆弱な操作の手順は残す）
- 重複して食い違う規則は、どちらかに揃える
- 自動フロー（review-pr / resolve-issue）の全自動性を損なわない
- 既存の導入先リポジトリの運用（ADR の採番など）を壊さない

## 検討した選択肢

### CLAUDE.md の Plan モード規則

- 「方針についてユーザーの承認を得てから着手する」を全セッションに適用する
- 適用範囲を「ユーザーから直接依頼されたタスク」に限定し、skill の自動フロー内の工程とサブエージェントを除外する
- 元の文言（「必ず Plan モードで開始する」）に戻す

### ADR 配置先

- `knowledge/adr/` に統一し、既存の別配置（`knowledge/D19/` など）は継続を許す
- `knowledge/D19/` の記述を戻す
- 移行手順を skill に書く

### HVE の完了報告

- ステップごとに 6 セクション報告（従来）
- ワークフロー完了時・停止時に 6 セクション報告し、ステップ単位の報告項目はそこへ集約する

## 決定内容

- **Plan モード規則**: ユーザーから直接依頼された 3 ステップ以上のタスクに限り、Plan モードで開始し承認を得てから着手する。skill の自動フロー内の工程とサブエージェントには適用しない（採用理由: 承認ゲートの意図を残しつつ、承認を求められない主体と全自動フローとの衝突を避けられる）
- **ADR 配置先**: knowledge 運用リポジトリは `knowledge/adr/` とする。既に別の配置先で ADR を運用しているリポジトリは、その配置先・採番・索引を継続する（採用理由: rules / skill 間の食い違いを解消しつつ、既存リポジトリの採番の分裂を防げる）
- **HVE の完了報告**: ワークフロー完了時、またはユーザーの判断を仰いで停止するときに 6 セクション報告を行う。各ステップのテンプレートと skill（hve-akm 等）が定める報告項目はこの報告に集約し、implement-flow の STOP は同ルールの 4 項目を使う（採用理由: 固定の中間報告の頻度は現行モデルでは過剰で、報告項目を失わずに回数を減らせる）
- **ui-approval**: 過去の判断による自動承認への移行計画（Phase 3b / 3c）を廃止し、UI 変更はすべて PO 承認とする。蓄積した判断軸は設計の参考にとどめる（採用理由: 未来のロードマップが実行指示と同列に書かれ、現行モデルが先取りして実行しうるため）
- **commit-workflow**: 既定のコミット形式を、履歴に合わせる方式（履歴が無い・混在時は Conventional Commits、件名はプロジェクトの言語）とする（採用理由: 旧既定の `[カテゴリ]` 形式が user-level の Conventional Commits 規約と食い違っていたため）
- **session-cost.py**: 未登録モデルの既定料金を旧 Opus 4（$15/$75）から Opus 5（$5/$25）に変える（採用理由: 未登録モデルが最も多いのは新しいモデルで、旧 Opus 4 料金では最大 3 倍以上の過大計上になるため。警告は従来どおり出す）
- 上記以外の整理（強調の平叙化、事故経緯・移行前提表現の削除、存在しない参照の修正、応答量を縛る件数上限の撤廃）は、各ファイルの差分で行う。成果物の粒度を定める方法論上の件数（ARD テンプレートのユースケース件数など）は対象外として残す

### 結果（Consequences）

- 良い結果: 過剰適用・硬直が減り、食い違う規則によるぶれが無くなる。HVE の報告回数が減る
- 悪い結果: 文面の変更でエージェントの振る舞いが変わるため、効果は運用で確認する必要がある。プロンプトはモデル世代ごとの成果物なので、次のモデル移行時に再監査が必要

## 選択肢の評価（Pros and Cons）

### Plan モード規則: 全セッションに適用する（却下）

#### メリット

- 承認ゲートが例外なく効く

#### デメリット

- `~/.claude/CLAUDE.md` 経由でサブエージェントにも効き、承認を求められない主体が止まる
- review-pr / resolve-issue の全自動フローと衝突する

### Plan モード規則: 元の文言に戻す（却下）

#### メリット

- 振る舞いが変わらない

#### デメリット

- 「必ず」の強調が残り、Plan モードの目的（承認ゲート）が文面に表れない

### ADR 配置先: `knowledge/D19/` の記述を戻す（却下）

#### メリット

- 既存の D19 運用リポジトリがそのまま動く

#### デメリット

- rules / hve-akm の `knowledge/adr/` との食い違いが残る

### ADR 配置先: 移行手順を skill に書く（却下）

#### メリット

- 配置先を 1 つに統一できる

#### デメリット

- 既存リポジトリの ADR の移動（git mv・採番・索引の張り替え）は、リポジトリごとの判断が要る。skill に一律の手順を書くのは過剰

### HVE の完了報告: ステップごとに報告する（却下）

#### メリット

- 途中経過が細かく見える

#### デメリット

- AAS だけで 10 回の定型報告になり、固定頻度の中間報告は現行モデルでは過剰
- 「成果物に含める」と読まれ、カタログ本体に見出しが混入しうる
