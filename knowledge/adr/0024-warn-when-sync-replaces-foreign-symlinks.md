# sync はリポの外を指す symlink を張り替え、元のリンク先と戻すコマンドを WARN に出す

## ステータス

Accepted — 2026-10-14

## 背景と課題

`sync-dotclaude.sh` は既存の `~/.claude/` のうち、別の場所を指す symlink（`CLAUDE.md`・`statusline.sh`・各 skill/hook など）を `ln -sfn` で張り直し、`fix` 行だけを出して終了コード 0 で終わっていた。symlink の `settings.json` も `rm` して生成版に置き換え、`migrate` と出すだけだった。一方、同じ名前の実体は WARN でスキップする（終了コード 2。ADR 0007）。symlink の場合だけ扱いが軽く、第三者の dotfiles 管理を黙って外しうる（Issue #49。#40 のレビューで検出）。

## 意思決定の要因

- 利用者が置き換えに気づけ、元に戻せること
- 作者の環境（リポを指す symlink の張り直し）での通常の同期は、今までどおり静かに通ること
- sync の目的（リポ版を `~/.claude` で効かせる）を果たすこと
- 追加のファイル・フラグを増やさないこと（no-overengineering）

## 検討した選択肢

- 方式: 張り替えて WARN に元のリンク先と戻すコマンドを出す／張り替えて記録ファイルにも追記する／実体と同じくスキップする／張り替えて WARN を出すだけ
- 対象の範囲: リポの外を指すリンク／別の hve-playbook の clone を指すリンクも除く／張り直すリンクすべて
- `settings.json` の symlink: 同じ扱い／リンク先の中身を bak に退避する／スキップする
- フラグ: 足さない／挙動を切り替えるフラグを足す

## 決定内容

選択した選択肢: **リポの外を指す symlink は張り替え、WARN に元のリンク先と戻すコマンド（シングルクォートで囲んだ `ln -sfn -- <元のリンク先> <リンク>`）を出し、終了コード 2 にする。`settings.json` の symlink も同じ扱いにする（リンク先の中身は変えない）。リポ配下を指すリンクは今までどおり静かに張り直す。フラグは足さない**。質問票の回答（`qa/sync-foreign-symlink-questionnaire.md`）と Plan の敵対的レビューによる。

- 「リポ配下」は、`readlink` の値が `REPO_DIR`（`pwd` の論理パス）の配下か、リンク先を物理パスに解決した結果が `pwd -P` で求めたリポの配下（リポそのものを含む）であるもの。物理パスは、リンク先がディレクトリとして存在すればパスそのもの、そうでなければ（ファイル・存在しないもの）親ディレクトリを `cd -P` で解決する（`dirname` は末尾の `.`・`..` を落とし、`-P` の無い `cd` は `..` を字面で処理してカーネルの解決とずれるため）。同じ clone を symlink 経由の別の綴り（macOS の `/tmp` と `/private/tmp` など）で起動したときに、全リンクで WARN が出続けないようにするため
- 相対パスのリンクは、リンクの位置に依存するのでリポの外として扱う（安全側）
- `.`・`..` を含む綴り（`$REPO_DIR/../dotfiles/x`・`$REPO_DIR/..` など）は、前方一致ではリポの外を指しうるので、論理パスの前方一致を使わず物理パスで判定する
- 旧 clone・別の clone を指すリンクはリポの外として扱う。別の clone から sync したことに気づける。main の clone の配下にある worktree を指すリンクは、前方一致で「リポ配下」になり静かに張り直す（main に戻るだけで実害が小さいので対処しない）
- 戻すコマンドは `printf %q` を使わず、シングルクォートで囲む（`'` は `'\''`）。macOS 標準の bash 3.2 の `%q` は非 ASCII のパスを不正な UTF-8 で出し、端末からコピーすると戻らないため。リンク先が `-` で始まってもオプションと解釈されないよう `--` を付ける
- `--prune` の対象（このリポ由来の dangling リンク）は変えない。WARN は張り替えた回だけ出て、次回からは正しいリンクなので静かに通る。dangling 検査の「このリポ由来か」は従来どおり論理パスの前方一致のままで、ここでの「リポ配下」の判定（物理パスも見る）とは揃えていない（揃えると `--prune` の対象が広がる）
- 挙動は `tests/test_sync_rules_agents.sh`（3c・3c-2・3c-3・3d）と `tests/test_sync_settings_overlay.sh`（11・11b）で固定する

### 結果（Consequences）

- 良い結果: symlink の置き換えにも、実体と同じく終了コード 2 で気づける。出力に元のリンク先と、貼ればそのまま戻るコマンドが残る。作者の通常の同期と、旧方式の `settings.json` の移行（リポを指す symlink）は今までどおり終了コード 0 で通る
- 悪い結果・既知の限界:
  - 元のリンク先は端末の出力にしか残らない。見落として出力を閉じると、元のリンク先を辿る手段は無い（リンク先の中身は残る）
  - 戻すコマンドで元のリンクに戻しても、次の同期で再び張り替わり（`settings.json` は生成版に置き換わり）、WARN が出る。`settings.json` の WARN では、残す設定を `settings.machine.json` に書くよう案内する
  - worktree から `~/.claude` に向けて sync すると、main の clone を指す全リンクで WARN が出る（別の checkout を指していたことに気づけるので意図どおり。作業ブランチでは `CLAUDE_HOME` を一時ディレクトリに向けて sync する運用）

## 選択肢の評価（Pros and Cons）

### 張り替えて WARN に元のリンク先と戻すコマンドを出す（採用）

#### メリット

- 終了コード 2 で気づけ、出力のコマンドで戻せる。リポ版も効く
- 追加のファイルもフラグも要らない

#### デメリット

- 元のリンク先は出力にしか残らない

### 張り替えて記録ファイルにも追記する

#### メリット

- 出力を見落としても元のリンク先を辿れる

#### デメリット

- 記録ファイルの置き場所・書式・掃除の管理が増える。終了コード 2 で気づける以上、需要が薄い

### 実体と同じくスキップする

#### メリット

- 利用者のリンクを一切変えない

#### デメリット

- リポ版が効かない。旧 clone を指していた作者の環境の移行が手作業になる

### 張り替えて WARN を出すだけ

#### メリット

- 実装が最小

#### デメリット

- 元のリンク先が分からず、戻せない

### 退避用の symlink を同じディレクトリに残す（検討の過程で棄却）

#### メリット

- 元のリンクがファイルシステムに残る

#### デメリット

- `skills/`・`hooks/` では退避したリンク自体が skill・hook として読み込まれうる

### `settings.json` のリンク先の中身を bak に退避する

#### メリット

- 実体の直接編集の退避（ADR 0006）と揃う

#### デメリット

- リンク先の中身は sync が変えないので、写しを作る必要が無い。戻すにはリンクを張り直すのが正しい
